[VULN-01] Unauthenticated Network-Exposed phpMyAdmin with Root Access
--------------------------------------------------------------------------------
* Severity:      CRITICAL (CVSS v3.1 Base Score: 9.8 - AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H)
* CWE:           CWE-306 (Missing Authentication for Critical Function)
                 CWE-668 (Exposure of Resource to Wrong Sphere)
* Location:
  1. include/phide/db/phpMyAdmin/config.inc.php (Lines 22-30):
     $cfg['Servers'][$i]['auth_type'] = 'config';
     $cfg['Servers'][$i]['user'] = 'root';
     $cfg['Servers'][$i]['password'] = '';
     $cfg['Servers'][$i]['AllowNoPassword'] = true;
  2. src/app/Window.cpp (Line 3578):
     php.exe -S 0.0.0.0:8081 -t "...\include\phide\db\phpMyAdmin"

* Technical Root Cause:
  The phpMyAdmin web server is started by binding PHP's built-in HTTP server to
  all network interfaces (0.0.0.0:8081) rather than loopback-only (127.0.0.1),
  combined with `auth_type = 'config'` and hardcoded `root` credentials with no
  password.

* How an Attacker Might Exploit It (Theoretical Attack Vector):
  1. Network / LAN Attack: Any attacker on the same Wi-Fi or local network can
     connect directly to http://<developer-lan-ip>:8081/ and is immediately
     logged into phpMyAdmin as the MySQL `root` superuser without authentication.
  2. Cross-Origin / DNS Rebinding Attack: Even if behind a NAT router, if the
     developer visits an attacker-controlled website in their browser, the page
     can use DNS rebinding against localhost:8081 to interact with phpMyAdmin's
     SQL execution endpoints.
  3. Escalation to Remote Code Execution (RCE): Once inside phpMyAdmin with root
     privileges, an attacker can execute arbitrary SQL statements. Using MariaDB
     file primitives (`SELECT ... INTO OUTFILE` or redirecting `general_log_file`
     into the active PHP project directory running on port 8080), the attacker
     can write a PHP script into the web root and achieve full Remote Code
     Execution under the Windows `Administrator` account.

* Remediation:
  - Bind phpMyAdmin strictly to loopback (`127.0.0.1:8081` or `localhost:8081`)
    unless LAN access is explicitly required.
  - Use `$cfg['Servers'][$i]['auth_type'] = 'cookie'` with a strong MySQL root
    password in non-isolated environments.

[VULN-02] MariaDB 10.4.32 Running with --skip-grant-tables on All Interfaces
--------------------------------------------------------------------------------
* Severity:      CRITICAL (CVSS v3.1 Base Score: 9.8 - AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H)
* CWE:           CWE-284 (Improper Access Control)
                 CWE-250 (Execution with Unnecessary Privileges)
* Location:
  1. C:\xampp\mysql\bin\my.ini (`skip-grant-tables` under `[mysqld]`)
  2. src/app/Window.cpp (Line 3526):
     mysqld.exe --defaults-file="C:\xampp\mysql\bin\my.ini" --skip-grant-tables --standalone --console

* Technical Root Cause:
  To bypass corrupted privilege tables, `mysqld.exe` is launched with
  `--skip-grant-tables` while listening on TCP port 3306 across all IPv4/IPv6
  interfaces (`0.0.0.0:3306` and `[::]:3306`) without `--bind-address=127.0.0.1`.

* How an Attacker Might Exploit It (Theoretical Attack Vector):
  Any host on the local network can open a direct TCP connection to port 3306
  using any MySQL client without supplying a password. Because grant tables are
  skipped, every connection is granted unrestricted database access, allowing
  complete database theft, schema destruction, or arbitrary file read/write on
  the host OS via `LOAD_FILE()` and `INTO OUTFILE`.

* Remediation:
  - Always pair `--skip-grant-tables` (if used temporarily) with
    `--bind-address=127.0.0.1` so remote TCP connections are rejected by the OS.
  - Repair the underlying `mysql.proxies_priv` and `mysql.user` system tables
    using `mysql_upgrade.exe` so standard privilege enforcement can be restored.

[VULN-03] OS Command Injection in SQL Auto-Import (Window::DoRunPhpApplication)
--------------------------------------------------------------------------------
* Severity:      HIGH (CVSS v3.1 Base Score: 8.8 - AV:L/AC:L/PR:N/UI:R/S:U/C:H/I:H/A:H)
* CWE:           CWE-78 (Improper Neutralization of Special Elements used in an OS Command)
* Location:
  src/app/Window.cpp (Lines 3662-3678):
    std::wstring sqlFile = m_dbSettingsModal.GetSqlFileName();
    ...
    std::wstring importCmd = L"cmd.exe /c \"\"" + mysqlExe.wstring() + L"\" -u root < \"" + sqlPath.wstring() + L"\"\"";
    CreateProcessW(NULL, cmdBuf.data(), ...);

* Technical Root Cause:
  `Window::DoRunPhpApplication` invokes `cmd.exe /c` and interpolates `sqlPath`
  (constructed from the opened project folder path and the configured SQL file
  name) directly into a shell command string without sanitizing or rejecting
  shell metacharacters (`"`, `&`, `|`, `>`, `<`).

* How an Attacker Might Exploit It (Theoretical Attack Vector):
  If a developer clones or extracts an untrusted project archive whose directory
  name contains shell metacharacters, or if a crafted SQL filename containing
  `"` and `&` is entered in the Database Settings modal, clicking the "Run"
  button causes `cmd.exe` to break out of the quoted path and execute arbitrary
  operating system commands with the privileges of the IDE process.

* Remediation:
  - Avoid `cmd.exe /c` shell redirection (`<`). Instead, open the `.sql` file in
    C++ using `CreateFileW` with `SECURITY_ATTRIBUTES::bInheritHandle = TRUE`,
    assign the file handle to `STARTUPINFOW::hStdInput`, and invoke `mysql.exe`
    directly via `CreateProcessW`.

[VULN-04] Hardcoded Static Cryptographic Secret (blowfish_secret) in phpMyAdmin
--------------------------------------------------------------------------------
* Severity:      HIGH (CVSS v3.1 Base Score: 8.1 - AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H)
* CWE:           CWE-798 (Use of Hard-coded Credentials)
                 CWE-321 (Use of Hard-coded Cryptographic Key)
* Location:
  include/phide/db/phpMyAdmin/config.inc.php (Line 11):
    $cfg['blowfish_secret'] = 'phide_pma_aes256_blowfish_secret_key_32b!';

* Technical Root Cause:
  The 32-byte `blowfish_secret` used by phpMyAdmin to encrypt and authenticate
  cookie-based session data is hardcoded to a static string across the entire
  IDE distribution instead of being generated per-installation using a CSPRNG.

* How an Attacker Might Exploit It (Theoretical Attack Vector):
  If a user switches `auth_type` to `'cookie'`, phpMyAdmin encrypts the user's
  MySQL password inside browser cookies using `blowfish_secret`. Because the
  secret key `'phide_pma_aes256_blowfish_secret_key_32b!'` is publicly known in
  the repository, any attacker who captures the cookie (via network sniffing on
  HTTP port 8081 or XSS) can immediately decrypt the user's plaintext database
  credentials or forge valid encrypted session cookies.

* Remediation:
  - Generate a random 32-byte secret per installation using `random_bytes(32)`
    or `BCryptGenRandom` on first launch.

[VULN-05] Native Memory Access Violation / Null-Pointer Dereference (0xc0000005)
          in MariaDB 10.4.32 (ACL_PROXY_USER::store_pk / get_column_grant)
--------------------------------------------------------------------------------
* Severity:      HIGH (CVSS v3.1 Base Score: 7.5 - AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:N/A:H)
* CWE:           CWE-476 (NULL Pointer Dereference)
* Location:
  C:\xampp\mysql\bin\mysqld.exe (MariaDB 10.4.32-MariaDB, `sql/sql_acl.cc`)
  Verified Crash Call Stack (captured via Windows Debugger `cdb.exe`):
    mysqld.exe!my_hash_first+0x29
    mysqld.exe!ACL_PROXY_USER::store_pk+0x12d
    mysqld.exe!get_column_grant+0x23a

* Technical Root Cause:
  When MariaDB 10.4.32 starts with an uninitialized or inconsistent internal
  `acl_proxy_users` hash structure (while `mysql.user` / `mysql.db` still load),
  any query that inspects column metadata (such as `SHOW COLUMNS FROM ...` or
  `SELECT * FROM INFORMATION_SCHEMA.COLUMNS`) invokes `get_column_grant()`,
  which calls `ACL_PROXY_USER::store_pk()` -> `my_hash_first()`. `my_hash_first`
  attempts to read offset `0x20` of a NULL pointer, raising an unhandled native
  exception `0xc0000005` (`STATUS_ACCESS_VIOLATION`) that terminates `mysqld.exe`.

* How an Attacker Might Exploit It (Theoretical Attack Vector):
  An attacker with even a minimal read-only database account (or an unauthenticated
  user triggering a web endpoint that queries table metadata, such as phpMyAdmin's
  ZeroConf `SHOW COLUMNS FROM phpmyadmin.pma__column_info` check) can reliably
  crash the entire MariaDB server process on demand, causing a complete Denial
  of Service (DoS) for all connected web applications.

* Remediation:
  - Upgrade MariaDB 10.4.32 to a supported LTS release (e.g., MariaDB 10.11+),
    and ensure `mysql_upgrade` validates all `mysql.*` grant tables on startup.

[VULN-06] Sibling Directory Path Traversal in LiveServer::HandleClient
--------------------------------------------------------------------------------
* Severity:      MEDIUM (CVSS v3.1 Base Score: 6.5 - AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N)
* CWE:           CWE-22 (Improper Limitation of a Pathname to a Restricted Directory)
* Location:
  src/server/LiveServer.cpp (Lines 261-267):
    std::filesystem::path canonical = std::filesystem::weakly_canonical(filePath, ec);
    std::filesystem::path rootCanonical = std::filesystem::weakly_canonical(root, ec);
    std::string canonStr = canonical.string();
    std::string rootStr = rootCanonical.string();
    if (canonStr.find(rootStr) != 0 || ...)

* Technical Root Cause:
  The directory traversal check in `LiveServer::HandleClient` verifies that the
  canonical target path starts with the string `rootStr` (`canonStr.find(rootStr) != 0`),
  without enforcing a path separator boundary (`\` or `/`) immediately after
  `rootStr`.

* How an Attacker Might Exploit It (Theoretical Attack Vector):
  Suppose the active workspace root is `C:\Users\Administrator\Downloads\project`.
  If a sibling folder exists named `C:\Users\Administrator\Downloads\project_private`
  or `C:\Users\Administrator\Downloads\project.bak`, its canonical path begins
  with the exact prefix `"C:\Users\Administrator\Downloads\project"`. An attacker
  can send an HTTP request containing URL-encoded `..` segments that resolve into
  the sibling directory, bypassing `canonStr.find(rootStr) != 0` and disclosing
  sensitive files outside the intended project root.

* Remediation:
  - Ensure `rootStr` ends with `std::filesystem::path::preferred_separator`
    before performing the prefix check, or use `std::mismatch` on path components.

[VULN-07] Wildcard CORS (Access-Control-Allow-Origin: *) + INADDR_ANY Binding in LiveServer
--------------------------------------------------------------------------------
* Severity:      MEDIUM (CVSS v3.1 Base Score: 6.5 - AV:N/AC:L/PR:N/UI:R/S:U/C:H/I:N/A:N)
* CWE:           CWE-942 (Permissive Cross-domain Policy with Untrusted Domains)
* Location:
  src/server/LiveServer.cpp:
  - Line 99:  `addr.sin_addr.s_addr = INADDR_ANY;`
  - Line 297: `<< "Access-Control-Allow-Origin: *\r\n"`

* Technical Root Cause:
  `LiveServer` binds to `INADDR_ANY` (`0.0.0.0`) and attaches the header
  `Access-Control-Allow-Origin: *` to every HTTP 200 response.

* How an Attacker Might Exploit It (Theoretical Attack Vector):
  While the developer is running `LiveServer` (ports 5500+), any untrusted
  third-party website opened in the developer's browser can issue cross-origin
  `fetch("http://localhost:5500/...")` requests to read source code, `.env`
  files, or configuration files inside the workspace root, because the wildcard
  CORS header instructs the browser to expose the response body to any origin.

* Remediation:
  - Restrict `Access-Control-Allow-Origin` to `http://localhost:<port>` or omit
    it by default, and block access to dot-files (`.env`, `.git/*`).

[VULN-08] Unauthenticated File-Modification Oracle & Recursive Directory Scan in Live-Reload Hook
--------------------------------------------------------------------------------
* Severity:      MEDIUM (CVSS v3.1 Base Score: 5.3 - AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:L)
* CWE:           CWE-400 (Uncontrolled Resource Consumption)
* Location:
  include/phide/server/phide_prepend.php (Lines 2-29)
  src/app/Window.cpp (Line 3380: `php -S 0.0.0.0:8080`)

* Technical Root Cause:
  The live-reload endpoint (`?__phide_mtime=1`) is exposed on `0.0.0.0:8080` and
  performs a synchronous `RecursiveIteratorIterator` scan over `getcwd()` on
  every request.

* How an Attacker Might Exploit It (Theoretical Attack Vector):
  Because PHP's built-in development server (`php -S`) is single-threaded and
  handles one HTTP request at a time, an attacker on the local network can send
  rapid concurrent requests to `/?__phide_mtime=1`, forcing repeated disk tree
  walks and blocking the single-threaded PHP server from responding to legitimate
  requests (Application-Layer DoS).

* Remediation:
  - Bind the PHP development server to `127.0.0.1:8080` (or verify
    `$_SERVER['REMOTE_ADDR'] === '127.0.0.1' || $_SERVER['REMOTE_ADDR'] === '::1'`
    before executing the directory scan in `phide_prepend.php`).
